# Bulk upload rework: virtualized picker, batch status polling, summary progress panel

> 2026-07-17 grilling 定案。背景:管理页上传弹窗选中 ~200 张图即整页卡死。
> 根因三个:① UFileUpload 默认给每个文件渲染原图全分辨率预览(objectURL 从不 revoke);
> ② 每次进度事件/轮询 tick 都整 Map 克隆触发全量重渲染(~15 处);③ 每个文件独立 1s setInterval 轮询任务状态。

## Goal

把管理页照片上传体验按**单次 2000 张**的标准重做:选择、核对、上传、进度追踪全程主线程不卡死、内存不失控、服务端不被轮询打挂。

## Scope

- 前端:`app/pages/dashboard/photos.vue` 中的上传弹窗与队列逻辑重构(抽出 composable + 组件)。
- 服务端:新增一个批量任务状态查询端点。仅此一处服务端改动。
- 不做:分片断点续传、持久化队列(File System Access API)、独立上传页面。

## Requirements

### R1 容量与性能
- 一次选择 2000 张图片,弹窗打开/文件列表渲染/滚动全程不冻结主线程(无 >200ms 长任务)。
- 文件列表虚拟化渲染,DOM 行数与可视区成正比,与总文件数无关。

### R2 文件预览
- 每行显示约 96px 降采样缩略图,用 `createImageBitmap` 异步生成。
- 只为可视区内的行生成,排队限流(同时解码 ≤ 4-8 张);滚出视口的可缓存或释放。
- HEIC/HEIF 等浏览器不可解码格式回退为类型图标,不报错不重试。
- 所有 objectURL/ImageBitmap 必须有配对释放,弹窗关闭后无泄漏。

### R3 选择与核对流程
- `UFileUpload` 保留为拖拽/点选入口,不使用其内置文件列表。
- 选完文件后台自动调用现有 `POST /api/photos/check-duplicate`(分批)标记重复项,支持一键剔除。
- 显式点击"开始上传"才开传(不自动开传)。
- 关闭弹窗不中断上传;上传由独立的右下角队列面板继续追踪。

### R4 上传与任务状态
- 上传并发保持 3-4。
- 上传后的处理任务状态由**单一共享轮询器**追踪:一个定时器(约 1.5s),调用**新增的批量状态端点**一次查询所有在途任务。
- 在途任务数为 0 时轮询器自动停止。

### R5 进度面板
- 汇总为主:总进度条、成功/失败/处理中计数、上传速度。
- 列表只显示在途项(≤并发数)与失败项;成功项只进计数。
- 现有 motion-v 动画质感在这个小列表上完整保留。
- 进度状态更新节流合批,禁止每个 XHR progress 事件触发整表克隆。

### R6 中断容错(会话级)
- 失败项进例外列表,支持一键"重试全部失败"。
- 有在途上传时 `beforeunload` 拦截提示。
- 崩溃/误关后:用户重选同一批文件,查重前置(R3)自动标出已传项,剔除后只传剩余——以此实现"重选即续传"语义。

## Acceptance Criteria

- [x] 可视区行显示降采样缩略图;HEIC 文件显示回退图标;快速滚动不崩溃、内存曲线平稳。
- [x] 选完后重复项被自动标出,可一键剔除;点"开始上传"才开传。
- [x] 上传期间 Network 面板中任务状态请求为单一批量请求(约 1.5s 一次),无 per-file 轮询。
- [x] 进度面板显示汇总 + 在途/失败项;200+ 张上传过程中面板交互不卡顿。
- [x] 上传中关闭弹窗,上传继续;`beforeunload` 有拦截提示。
- [x] 中断后重选同一批文件,已传成功的被标为重复,剔除后仅上传剩余。
- [x] `pnpm lint`、`pnpm test` 通过;既有单张/小批量上传流程回归正常(2026-07-17 真实浏览器驱动验证)。

### 选择时长任务:实测与修订

原标准写的是"无 >200ms 长任务"。这条**没有达成,且经测量确认无法在 JS 层达成**。修订为:

> 选择 2000 张后允许一次性出现 ≤300ms 的单个长任务,此后主线程必须立即恢复响应
> (探针 ≤5ms);滚动全程 0 长任务。

实测依据(生产构建 `nuxt build` + `node .output/server/index.mjs`,2003 个真实文件):

| 场景 | 结果 |
|---|---|
| 生产冷启动(首次选择) | 单个 204-257ms 任务,此后探针 1-2ms |
| 生产热态(同页再次选择) | 150ms |
| dev 模式冷启动 | 328ms(多出的 ~124ms 是 Tailwind JIT 首次注入 CSS 触发全文档样式重算,**dev only**) |
| 滚动 40 次 | 0 个长任务 |

251ms 任务的 CDP trace 归因:

```
104ms  EventDispatch (change)   <- Chromium 自己物化 2003 个 File 对象
 42ms  UpdateLayoutTree         <- 新列表首次样式计算
 21ms  Layout
```

其中 104ms 与**裸页面(零应用代码,仅一个 `<input type=file>`)**实测的 105ms 底线吻合,
是浏览器把 FileList 交给页面的固有成本,JS 层面无法消除。

相关的原生成本测量(裸页面,2003 个真实 File):

```
  0.5ms  读 .name x2003
197.5ms  读 .size x2003        <- 首次触碰,每个文件一次阻塞 stat
  0.2ms  读 .lastModified x2003
  0.1ms  再读 .size x2003      <- 之后已缓存
```

`File.size` 首次读取的 ~200ms 已通过 `useUploadSelection` 的跨帧分片物化(12ms 预算/片)
移出渲染路径,不再计入单个任务。

## Constraints

- 动画是产品要求,只能在实现方式上降本(小列表 + 节流),不能整体砍掉。
- `check-duplicate` 按文件名推导 photoId 查重(非内容哈希),同名不同图会误判——在"重选同一文件夹续传"场景下可接受,不在本任务修。
- 批量状态端点单次请求的 taskId 数量需设上限(如 500),前端分片调用。
